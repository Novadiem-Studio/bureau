# Challenger pattern analysis: method and output format

How to mine the run logs for recurring Challenger findings, tag them consistently, and produce a
comparable patterns report. The output of this method is `docs/evaluation/architect-challenger-patterns.md`.

The point of writing the method down is **comparability**. The patterns report is only useful as a
trend if every refresh uses the same taxonomy and the same output shape. If a future pass invents
its own pattern tags or reorders the tables, the before/after comparison that justifies the
self-check work (see `ideas/not-started/architect-challenger-pre-flight-v2.md`) becomes noise. So
the taxonomy below is frozen: extend it by appending new tags with definitions, never by renaming
or merging existing ones.

## When to run

- After every ~5 new completed runs, or quarterly, whichever comes first.
- Before and after landing any change aimed at reducing rework (the self-checks, an agent-prompt
  revision, a new convention), to measure whether it moved the needle.

## The two frozen taxonomies

Every finding gets exactly one **artifact tag** and one **pattern tag**.

### Artifact tag (where the defect lived)

| Tag | Meaning |
|---|---|
| `spec-body` | Requirements / functional-requirements prose |
| `architecture-section` | The Architecture section of spec.md |
| `plan` | plan.md (phases, chunks, deliverables) |
| `prompt` | prompts.md (a coder-facing prompt) |
| `acceptance-criteria` | An AC item |
| `edge-cases` | The Edge Cases / Failure Modes section |
| `assumptions` | The Assumptions section |
| `open-questions` | An open question |

### Pattern tag (what kind of defect)

Frozen at 17. Append-only.

| Tag | Meaning |
|---|---|
| `missing-edge-case` | Happy path specified; a null/zero/empty/oversize/platform branch left unhandled |
| `internal-contradiction` | Two places in one artifact assert mutually exclusive facts (count, name, rule) |
| `wrong-api-shape` | Field, endpoint, return type, or signature does not match live code |
| `under-specified` | A component or rule is named but not defined precisely enough to build |
| `wrong-call-site` | An edit is directed at the wrong file, function, or line |
| `deployment-path-gap` | An asset/route/file assumed reachable at runtime is not at the served path |
| `ac-implementation-mismatch` | An AC asserts a value the implementation cannot produce as written |
| `stale-name` | A symbol/file/key refers to something renamed, removed, or from a prior draft |
| `deferred-not-documented` | A punted behavior/dependency left as a comment or silence, not a named callout |
| `external-dependency-unstated` | A new library/service/runtime capability assumed present with no provisioning step |
| `env-config-unstated` | An env var / base URL / endpoint missing from .env.example or unverified |
| `import-missing` | A symbol used in code with no import present |
| `test-coverage-gap` | A new code path or behavior with no test |
| `async-sync-mismatch` | An async/sync contract that does not match the framework |
| `reuse-missed` | An existing helper/pattern not reused where it should be |
| `false-positive-risk` | A check/rule that would fire on legitimate cases |
| `caller-cant-supply` | A tool/API requires a value the caller has no way to provide |

If a finding genuinely fits none of these, add a new row here with a one-line definition and note
it in the report's changelog. Do not stretch an existing tag.

### Severity and action

- Severity: `BLOCKER` or `WARNING` (the Challenger's own label). A withdrawn/downgraded blocker is
  tagged at its final severity.
- Action: `FIXED`, `ACKNOWLEDGED`, or `OVERRIDDEN` (what the Conductor did).

## Extraction procedure

1. List every `output/runs/*/log.md`.
2. In each, find the Challenger sections (headings containing "Challenger" or "Challenger review").
   A run may have multiple passes (round 1 spec+plan, round 2 prompts, delta reviews); count each.
3. Skip runs with no Challenger pass (pure planning or analysis-only runs); note them as skipped.
4. For each Blocker and Warning, record: run slug, severity, one-line finding summary, action,
   artifact tag, pattern tag.
5. Delegating this to a subagent is fine and recommended (the corpus is large). Hand it this doc so
   it uses the frozen taxonomy verbatim.

## Output file format

`docs/evaluation/architect-challenger-patterns.md`. Required sections, in this order. Keep column order and
sort order fixed so two refreshes diff cleanly.

1. **Title.**
2. **Metadata block** (a fenced or bulleted header):
   - `Generated:` absolute date
   - `Runs covered:` date range + count, plus count skipped
   - `Challenger passes:` total
   - `Findings:` total (blockers / warnings)
   - `Generated by:` session or method note
3. **Metric snapshot** — average `critic_loops.architect` and `critic_loops.prompts` across the
   covered runs (see below). This is the trend line; it must be present even if approximate.
4. **Pattern frequency table** — `Pattern | Count`, sorted count descending. Use the frozen tags.
5. **Top patterns described** — the highest-frequency patterns, one short paragraph each, with one
   concrete example pulled from a log.
6. **Pre-flight checklist** — the current owner-split checks (Architect vs Spellwright), each
   carrying its pattern tag and hit count. Mirrors the live state of the self-check idea/build.
7. **Full findings table** — `Run | Sev | Finding | Action | Artifact | Pattern`, grouped by run in
   chronological order.
8. **Changelog** — one line per refresh: date, runs added, any new pattern tag, notable shifts in
   the frequency ranking.

## The metric

The report's reason to exist is the rework trend. For each covered run, read `state.json`:

- `critic_loops.architect` (integer)
- `critic_loops.prompts` (integer)

Report the mean of each across the covered set in the Metric snapshot. When comparing two refreshes,
the question is simple: did the averages fall after a rework-reduction change landed? If a change
did not move them, it was theater and should be reconsidered.

Caveat: `critic_loops` counts adjudicated revision loops, not raw findings. A run can absorb several
acknowledged warnings in zero loops. So track both the loop averages (the headline) and the total
findings count from the metadata block (the texture).

## Outputs and naming

- Method (this file): `docs/evaluation/challenger-pattern-analysis.md`.
- Report: `docs/evaluation/architect-challenger-patterns.md` (overwritten each refresh; history lives in its
  changelog section and in git).
